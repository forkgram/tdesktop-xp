# Names that Windows XP Professional x64 Edition exports and Windows XP SP3 x86
# does not. Consulted by xp\xpsafe.ps1 ONLY while xp\exports-x64 is missing, to
# check a 64-bit binary against the 32-bit tables without failing it for an API
# its actual target really has.
#
#   one entry per line, "dll.dll!FunctionName", # starts a comment
#
# XP x64 is NT 5.2 - the Server 2003 SP2 kernel - so its API surface is a
# SUPERSET of XP SP3's. That is what makes the fallback safe in the direction
# that matters: a Vista+ entry point is absent from both, so it still fails the
# gate. It is only unsafe in the harmless direction, reporting a name that does
# exist there. This file is the list of those exceptions.
#
# It ships EMPTY on purpose. Every line here weakens the gate, so a name goes in
# only after its presence has been READ OFF a real XP x64 kernel32 - never from
# an "minimum supported server: Windows Server 2003" line in the documentation,
# which describes the API and not the export table of a particular image. Let
# the CI run report what the build actually imports and add those, verified.
#
# The likely candidates, left commented out until checked. The Fls* family and
# the NUMA call are thunked away by xp\fpcompat\xpfls64.asm, so a correct build
# should not import them at all - if one of these turns up in the report, that
# thunk is not doing its job and the fix is there, not here:
#
# kernel32.dll!FlsAlloc
# kernel32.dll!FlsFree
# kernel32.dll!FlsGetValue
# kernel32.dll!FlsSetValue
# kernel32.dll!GetNumaHighestNodeNumber
# kernel32.dll!GetSystemWow64DirectoryW
# kernel32.dll!SetThreadStackGuarantee
# kernel32.dll!GetThreadId
#
# The whole file becomes dead once xp\exports-x64 exists:
#   powershell xp\dump_xp_exports.ps1 -Arch x64 -From <dir with the 64-bit DLLs>
